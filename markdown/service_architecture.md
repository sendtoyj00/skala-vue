## 1. 서비스 컨셉

> **이 강아지가 지금 산책해도 되는지를 대신 판단해 주는 서비스.**

기온·습도·풍속을 나열해서 해석을 사용자에게 맡기지 않는다. 개체 특성(견종·체중·연령)과 날씨를 결합해 **얼마나, 언제 나갈 수 있는지**를 서비스가 먼저 판정해 제시한다. 화면의 최종 산출물은 숫자가 아니라 **"지금 15분, 그늘 위주로" 같은 실행 가능한 지시**다.

### 1.1 이전 컨셉에서 무엇을 바꿨는가

직전 컨셉은 "지금 밖에 나가도 되는지를 대신 판단해 주는 날씨 서비스"였다. 판정 구조(입력→판정→행동 권고)는 그대로 유지하고 **주어만 좁혔다.** 피벗이 아니라 상속이다.

좁힌 이유는 두 가지다.

**① 이전 컨셉은 기능을 탈락시키지 못했다.** 컨셉 문장의 유일한 존재 이유는 기능 채택/탈락 판정을 가능하게 하는 것인데, "나가도 되는가"는 주어가 비어 있어 누가 무엇을 하러 나가는지가 없었다. 그 결과 어떤 기능이든 "판단에 도움이 된다"고 주장할 수 있었다.

실제 증거: 직전 기능표에서 대기질(F-12)의 채택 근거가 **"판단 근거 추가"** 한 줄이었다. 이건 근거가 아니라 동어반복이고, 같은 논리로 자외선·꽃가루·기압을 무한히 넣을 수 있었다. 예보(F-11)는 "그래프 자체는 판정을 만들지 않는다"며 한 번 탈락시킨 뒤 다시 P1로 채택해 판단이 왕복했다.

**② 판정이 사용자가 이미 아는 것을 반복했다.** 이전 대표 산출물은 "제주: 폭우, 외출을 삼가세요"였다. 폭우는 창밖을 보면 안다. 컨셉은 지켰지만 판정이 만들어내는 정보 가치가 얇았다.

견주 판정의 대표 산출물은 **"기온 31℃, 추정 지면온도 58℃ — 발바닥 화상 위험. 저녁 7시 이후 15분"**이다. 기온 31도에서 아스팔트가 58도라는 것은 대부분 모른다. 판정이 실제로 새 정보를 만든다.

### 1.2 이 방향이 기존 배제 기준에 걸리지 않는 이유

직전 문서 2절은 "특정 취미 종사자"를 대상에서 배제했다. 사유는 **"종목별 전용 지표가 필요해 판정 규칙이 종목 수만큼 늘어난다"**였다.

견주 방향은 이 사유에 걸리지 않는다. 종목을 하나 더 얹는 것이 아니라 판정 규칙 전체를 그 하나로 **교체**하므로 규칙 수가 늘지 않는다. 반대로 "범용 판정 + 견주 모드"를 옵션으로 병행하는 안(하이브리드)은 정확히 이 배제 사유에 해당하므로 **채택하지 않는다**(1.4).

또한 견주는 취미 종사자가 아니다. 산책은 하루 1~2회 강제되는 일과이며, 직전 문서의 U-1(출퇴근 직전 확인자)과 같은 반복 구조를 갖되 동기가 더 강하다.

### 1.3 기능 채택 기준

```text
새 기능 후보
  → 이 기능이 "이 개가 지금 나가도 되는가" 판정을 직접 만드는가?  Yes → P0 후보
  → 판정의 정확도 또는 개체 맞춤도를 올리는가?                   Yes → P1 후보
  → 서비스 운영에 필요한 최소 요건인가?                          Yes → P2 후보
  → 위 전부 No                                                → 채택 안 함
```

> 판정에 쓰이지 않는 값은 화면에 넣지 않는다. 값을 추가하려면 그 값을 쓰는 판정 규칙을 먼저 추가한다.

새 컨셉의 판별력 검증 — 직전 컨셉에서 판단이 왕복하거나 모호했던 후보들이 즉시 갈린다:

| 후보 | 이전 판정 | 새 판정 |
| --- | --- | --- |
| 대기질 | "판단 근거 추가"(동어반복) | **채택(F-12)** — 개는 지면 30cm에서 호흡해 사람 기준 농도와 노출량이 다르다 |
| 시간별 예보 | 탈락 후 재채택(왕복) | **채택·P0 승격(F-11)** — "저녁 7시 이후"가 최종 산출물 그 자체다 |
| 지역 비교 | P2, "배치 문제일 수 있음"(보류) | **폐기(F-13)** — 견주는 자기 동네만 본다 |
| 자외선 지수 | 판정 불가 | **탈락** — 털로 덮여 있어 판정을 바꾸지 않는다 |

**채택하지 않는 기능**(이유와 함께 기록해야 재현 가능한 기준이 된다):

| 후보 | 탈락 이유 |
| --- | --- |
| 산책 기록·GPS 트래킹 | 지나간 산책을 기록할 뿐 다음 판정을 만들지 않는다 |
| 반려견 SNS·사진 공유 | 체류 시간을 늘리는 기능이지 판정 개선 기능이 아니다 |
| 산책 메이트 매칭 | 다른 서비스다. 판정과 무관 |
| 동물병원·펫샵 찾기 | 위치 정보 서비스이지 판정이 아니다 |
| 사료·용품 추천 | 날씨 판정과 인과가 없다 |
| 질병·증상 진단 | 수의학적 판단이다. 11절 책임 경계에서 명시적으로 배제한다 |
| 실시간 기상 레이더 | 원시 관측 화면이라 해석을 사용자에게 되돌려준다 |
| 기상 용어 사전 | 해석을 사용자에게 맡기지 않는다는 컨셉과 반대. 문구가 불충분하다는 신호로 읽는다 |

### 1.4 하이브리드(범용 + 견주 모드)를 채택하지 않는 이유

직관과 달리 하이브리드가 가장 나쁘다. 이 문서군의 규칙 셋과 동시에 충돌한다:

1. **판정 주체가 둘이 된다.** `WeatherBadge`("외출을 삼가세요")와 산책 판정("15분 가능")이 한 화면에서 각각 판단을 주장한다. 둘이 다른 답을 내는 경우가 실제로 있다 — 사람은 괜찮은데 개는 위험한 31℃가 정확히 그 경우다.
2. **"판정 함수는 1개만 존재한다"**(4절)를 어긴다. 판정이 2벌이 되고, 이 프로젝트는 이미 판정 규칙이 4벌로 흩어져 화면 문구와 어긋났던 이력이 있다.
3. **"화면당 최강 강조 1개"**([design_architecture.md](./design_architecture.md) 2절)를 어긴다.

> 컨셉은 좁히거나 유지할 수는 있어도, 둘을 동시에 주장할 수는 없다.

## 2. 사용자와 사용 목적

사용자는 직업이 아니라 **사용 상황**으로 나눈다. 같은 사람이 아침엔 짧은 배변 산책을, 주말엔 긴 나들이를 판단하기 때문이다.

| ID | 유형 | 언제/어디서 | 필요한 판단 | 연결 기능 | 상태 |
| --- | --- | --- | --- | --- | --- |
| U-1 | 매일 산책 견주 | 현관 앞, 하루 1~2회 | 지금 나가도 되는가, 몇 분인가 | F-23 판정, F-24 지시문 | `[예정]` |
| U-2 | 시간대 조정 견주 | 실내, 낮 시간 | 지금 말고 언제 나갈까 | F-11 예보, F-26 타임라인 | `[예정]` |
| U-3 | 고위험 개체 보호자 | 여름·겨울 상시 | 단두종·노령견이 견딜 수 있는가 | F-25 지면온도, F-27 프로필, F-28 특성 | `[예정]` |
| U-4 | 다견 가정 | 산책 직전 | 어느 아이 기준으로 맞출까 | F-29 개체 전환 | `[예정]` |
| U-5 | 첫 반려 시작자 | 임의 | 애초에 기준이 뭔가 | F-24 지시문, F-30 근거 안내 | `[예정]` |

U-3이 이 서비스의 **핵심 사용자**다. 단두종(불독·퍼그 등)과 노령견은 같은 날씨에서 위험도가 급격히 다른데, 일반 날씨 앱은 이 차이를 표현할 수단이 없다. 서비스의 존재 이유가 가장 선명한 지점이다.

**대상으로 삼지 않는 사용자**: 전문 훈련사·브리더(개체별 정밀 관리가 필요해 판정을 축약하는 이 서비스와 방향이 반대), 질병·수술 회복 중인 개의 보호자(수의학적 판단 영역 — 11절), 축산·사역견 종사자(법적 책임 수준의 신뢰 보증이 필요), 데이터 재가공 개발자(판정 이전의 원본을 원한다).

## 3. 기능 목록과 우선순위

### 3.1 기능 ID 체계

`F-` + 두 자리 번호. 발급 순서대로 부여하고, **폐기해도 재사용하지 않으며 재배열하지 않는다**(행을 지우지 않고 `[폐기]`로 표기).

컨셉이 바뀌었다고 ID를 다시 매기지 않는다. 이전 기능이 어떤 판단을 거쳐 강등·폐기됐는지가 남아야 같은 논의를 반복하지 않는다.

### 3.2 우선순위 정의

| 등급 | 판정 문장 |
| --- | --- |
| P0 | 이 기능을 빼면 컨셉 문장("이 개가 나가도 되는지 판단")이 성립하지 않는다 |
| P1 | 컨셉은 성립하지만 정확도·맞춤도가 크게 떨어진다 |
| P2 | 판정과 무관, 운영상 필요 |

> 어떤 기능의 우선순위는 그 기능이 의존하는 기능의 우선순위보다 높을 수 없다.

## 4. 기능 작동 기준

> Store의 action 이름과 인자는 이 절의 규칙에서 도출된다. 규칙 없이 Store부터 만들면 이름이 `setX`로 뭉개진다.

### 4.1 F-23 산책 가능 판정 — 컨셉의 핵심

**입력**: `Weather`(기온·습도·풍속·상태) + `GroundTemp`(추정) + `DogTraits`(4축) — 셋 다 필수.

**출력**: 단일 boolean이 아니라 구조체다.

```js
WalkVerdict = {
  level: 'good' | 'caution' | 'limited' | 'unsafe',
  maxMinutes: number | 0,
  bestWindows: [{ from, to }],   // F-26이 채운다
  reasons: [{ code, threshold, actual }],
}
```

**출력이 boolean이 아닌 이유**: 직전 문서는 "위험 등급은 2단계로 시작한다 — 소비처가 boolean으로 충분하다"고 결정했다. 이 근거가 무너졌다. 견주에게 유용한 답은 "가능/불가"가 아니라 **"15분 이내, 그늘 위주로"**이고, `maxMinutes`가 없으면 F-24 지시문을 만들 수 없다.

`reasons`를 배열로 두는 이유는 직전 문서와 같다 — 조건이 동시에 성립할 때(지면 고온 + 고습) 조합 전용 문구를 만들면 조건 수에 따라 분기가 기하급수로 늘어난다. 조건 N개에 문구 N개만 둔다.

**판정 함수는 1개만 존재한다.** 화면 문구는 임계값을 직접 타이핑하지 않고 같은 출처를 참조한다 — 직전 프로젝트에서 경보 화면이 "60m/s 이상"이라 적었지만 실제 판정은 50이었던 실패를 반복하지 않는다(`weatherRules.js:5` vs 화면 문구).

### 4.2 F-25 지면온도 — 서비스 고유값이자 최대 리스크

여름철 아스팔트 표면온도는 기온보다 크게 높다. 이 격차가 견주에게 가장 중요한 정보다.

**정정**: 이전 개정은 "어떤 날씨 API도 지면온도를 제공하지 않는다"고 단정했으나 사실이 아니다. **기상청_도로기상관측자료**(data.go.kr, 활용신청번호 15159045)가 노면온도(`노면온도` 필드)를 실측 제공한다 — 노면상태·시정·습도·기온·풍향풍속 등 14개 요소와 함께, 전국 고속도로 366개 지점에서 관측한다.

다만 이 API를 F-25의 **단독** 데이터 원천으로 쓸 수는 없다. 관측점이 고속도로 366곳으로 한정돼 주거지 인근 커버리지가 없다 — 대부분의 사용자 위치는 관측점에서 멀다. 그래서 이중 구조로 간다:

| 상황 | 데이터 원천 | 표기 |
| --- | --- | --- |
| 인근(반경 15km 이내, 잠정치)에 관측점 존재 | 기상청_도로기상관측자료 실측값 | "노면 관측값"(추정 라벨 불필요) |
| 관측점이 멀거나 없음(대다수 사용자) | 기온 + 일사 보정(날씨 상태·시간대 기반) 추정 | **"추정" 필수 병기** |

**`[현재]` 이중 구조가 실제로 동작한다** — `domain/groundTemp.js`(`findNearestRoadStation`, `estimateGroundTemp`) + `composables/useGroundTemp.js`. 반경 15km는 공식 기준이 아니라 이 구현이 택한 잠정치다(고속도로 관측망 밀도상 도심 사용자는 대부분 이 반경 밖에 있어 추정 경로로 폴백하는 것이 정상 동작 — 실측 확인: 서울 시청 기준 15km 이내 관측점 0개, 가장 가까운 관측점도 30km 이상). 이 반경값의 재검토는 `[결정 필요]`로 남는다.

**`[현재]` API 응답 형식의 실측 결과**: 기상청_도로기상관측자료는 JSON이 아니라 EUC-KR 인코딩된 텍스트 표를 반환한다(mode=3 기준 콤마 구분, mode=1 기준 콤마 없는 고정폭 공백 구분 — 두 모드의 구분자가 다르다는 것을 실측으로 확인했다). 파싱은 `api/roadWeatherApi.js`가 전담한다.

**`[현재]` 이 API는 CORS를 지원하지 않는다** — `Access-Control-Allow-Origin` 헤더가 없다(curl로 실측 확인). 브라우저에서 직접 axios/fetch로 호출하면 차단된다. 개발 서버는 `vite.config.js`의 프록시로 우회하지만, 정적 빌드 배포에는 이 프록시가 없다. **이 프로젝트에는 백엔드가 없다는 9절의 전제와 정면으로 부딪히는 지점이며, 운영 배포 방식은 `[결정 필요]`로 남는다**(서버리스 프록시 함수 신설 등).

| 결정 | 내용 |
| --- | --- |
| 산출 방식(추정 경로) | 기온 + 일사 보정(날씨 상태·시간대 기반) |
| 보정 축소 조건 | 흐림·비는 보정 감소, 야간은 보정 0에 수렴 |
| 표기 | 추정 경로는 **반드시 "추정"을 병기한다.** 관측값처럼 보이게 하지 않는다 |
| 판정 사용 | `level`과 `maxMinutes`에 직접 반영 |
| 근거 기록 | 보정 계수·판정 임계값의 출처를 `domain/walkRules.js` 주석에 남긴다 `[현재]` |

> 추정값을 관측값처럼 표시하지 않는다. 정확도보다 정확도의 한계를 밝히는 것이 먼저다.

**임계값은 확보됐다** `[현재]`. `domain/walkRules.js`가 다음 근거로 채택한다:

- **44℃ / 51℃(주의/위험 경계)**: Henriques FC, *"Studies of Thermal Injury V"*, Arch Pathol. 1947 — 피부 화상 역학의 고전 참조치(44℃ 미만은 장시간 접촉해도 손상 없음, 44~51℃는 온도 1도당 손상 속도 배가, 51℃ 이상은 표피 손상이 거의 즉시 발생). AKC/AAHA 소비자 가이드(포장도로 51.7℃에서 60초 내 화상)와 대한민국 정책브리핑(2023, 기온 25℃일 때 노면 약 50℃)이 같은 자릿수로 교차 검증된다.
- **29℃(기온 주의 경계)**: AKC·AAHA 공동 가이드 — 기온 85°F(≈29.4℃) 이상이고 노면이 식을 기회가 없으면 산책이 위험할 수 있다.
- **80%(습도 경계)**: 캐닌 열스트레스 연구 공통 소견 — 개는 헐떡임의 증발냉각으로 체온을 조절하는데, 상대습도 80% 이상에서 이 기전이 급격히 실패한다.

이 값들은 사람/일반 소비자 가이드 기반 1차 근거다. `[결정 필요]`로 남는 것은 **수의학 원저 논문으로 재검증**이지, "근거 없음" 상태는 아니다. API 활용신청은 완료됐다(`authKey` 발급 확인) — 관측점 반경 기준은 위에서 15km 잠정치로 채택했다.

### 4.3 F-05/F-06 승계 — 역할 강등

`isDangerWeather`(`weatherRules.js:10-11`)는 유지하되 **최종 산출물이 아니라 F-23의 입력 하나**가 된다. 폭우·강풍은 견종과 무관하게 산책을 막으므로 개체 특성보다 먼저 걸러지는 조건이다.

경보 목록(F-06)은 "위험 날씨 지역"이 아니라 **"지금 산책이 불가한 지역"**으로 문구를 재정의한다. 판정 주체는 여전히 F-23 하나다.

직전 문서가 지적한 결함 — 판정이 `status === '폭우'` 문자열 정확 일치라 API 응답 문구가 바뀌면 조용히 전부 거짓이 된다는 문제 — 는 **`[현재]` 해소됐다**. `weatherRules.js:classifyStatusCode`가 OpenWeatherMap의 수치 조건코드(`weather[0].id`)를 `statusCode`(STORM/RAIN/SNOW/…)로 정규화하고, `isDangerWeather`·`walkRules.js`는 전부 `statusCode`를 본다. 한글 설명 문구(`status`)는 표시 전용으로만 남는다.

**`[현재]` 강풍 임계값도 재보정했다** — 이전 `DANGER_WIND_SPEED=50`은 목업 windSpeed(10~60, km/h 감각)에 맞춘 값이라 실제 m/s 데이터(대부분 0~10 범위)에서는 사실상 발동하지 않는 죽은 조건이었다(6절이 이미 이 재조정 필요성을 지적해 뒀다). 기상청 강풍주의보 기준(평균풍속 14m/s 이상)으로 재보정했다.

### 4.4 F-28 견종 특성 정규화 — 조합 폭발 방지

> 판정 함수는 견종 이름을 모른다.

견종 200종 × 날씨 조건을 직접 매핑하면 직전 문서가 경고한 "조건이 늘수록 분기가 기하급수" 상황이 그대로 재현된다. 견종을 **4개 특성 축으로 환원**한 뒤 판정은 축만 본다.

```js
DogTraits = {
  brachycephalic: boolean,              // 단두종 — 호흡기 구조상 체온 조절 취약
  coatType: 'single' | 'double',        // 이중모 — 더위 취약
  weightClass: 'small' | 'medium' | 'large',  // 소형 — 지면 근접, 체온 변화 빠름
  ageClass: 'puppy' | 'adult' | 'senior',     // 유·노령 — 전반 취약
}
```

| 결정 | 내용 |
| --- | --- |
| 변환표 위치 | 한 곳에만 둔다(`domain/breeds.js`) |
| 미등록 견종 | 오류가 아니라 **기본값(adult/medium/single/false) + 안내**. 서비스가 멈추지 않는다 |
| 축 추가 | 축을 늘리려면 그 축을 쓰는 판정 규칙을 먼저 추가한다(1.3 원칙과 동일) |
| 믹스견 | 사용자가 축을 직접 선택할 수 있게 한다(견종 선택은 축 입력의 편의 수단일 뿐) |

이 구조 덕분에 견종이 200종이 되어도 판정 규칙은 4축 그대로다.

### 4.5 F-24 산책 지시문

- 판정 근거(`reasons`) 1건당 문구 1개. 조합 전용 문구를 만들지 않는다.
- 동시 노출 최대 **2개**(우선순위: 지면온도 > 강수·강풍 > 기온·습도 — 즉시성 기준).
- **단정하지 않는다.** "괜찮습니다"가 아니라 "15분 이내, 그늘 위주로"처럼 조건부로 쓴다(11절 책임 경계). 조건부 문구가 사용자에게도 더 유용하다.
- 판정 불가 상태(`unsafe`)에도 대안을 제시한다 — "실내 놀이 권장" + F-26이 제안하는 다음 가능 시간.
- **임계값을 문구에 노출하지 않는다.** 기준 설명은 F-30 안내에서 한 번만 한다.

## 5. 사용자 흐름과 기능 간 연계

### 대표 흐름

**A. 첫 방문 → 프로필 등록 → 판정** `[예정]`: `/` 진입 → 프로필 없음 안내 → 견종·연령·체중 입력 → 즉시 판정 표시. 이탈 지점: 견종을 모르거나 믹스견(4축 직접 선택으로 우회), 입력 항목이 많다고 느낌(필수 3개로 제한).

**B. 매일 아침 재방문** `[예정]`: `/` 진입 → 프로필이 이미 있으므로 **바로 판정**. 이 흐름이 가장 자주 발생하므로 홈은 목록이 아니라 판정이 첫 화면이어야 한다(F-01이 P2로 내려간 실질적 이유).

**C. 지금 위험 → 시간대 조정** `[예정]`: 판정이 `unsafe`/`limited` → 타임라인에서 가능 시간대 확인 → "저녁 7시 이후". **이 흐름이 끊기면 서비스가 "안 된다"만 말하는 서비스가 된다.** F-26이 P0인 이유다.

**D. 다견 가정** `[예정]`: 기본은 최취약 개체 기준 판정 + 기준 개체 명시 → 필요 시 개체 전환.

**E. 판정 근거 확인** `[예정]`: 판정 → "왜?" → 지면온도·습도·견종 특성이 각각 얼마나 기여했는지 → 면책 안내(F-30).

### 기능 간 연계

```text
[도시 마스터] → Weather(현재관측) ┐
                Forecast[예정] ────┼→ GroundTemp[예정] ┐
[반려견 프로필] → DogTraits ───────┴──────────────────┴→ WalkVerdict → 지시문/타임라인
```

> 산책 판정은 화면이 아니라 데이터 변환이다. 지시문·타임라인·경보 목록은 그 결과를 다른 방식으로 보여줄 뿐 각자 판정하지 않는다.

직전 프로젝트에서 실제로 발생한 문제 — 같은 데이터를 여러 곳이 각자 갖는 것 — 는 `weatherStore`(`weatherStore.js:10`) 도입으로 해소됐다. **프로필에서 같은 실수를 반복하지 않는다**: 반려견 데이터의 단일 출처는 `dogStore` 하나이며, 판정에 필요한 결합은 화면이 아니라 composable에서 한다([vue_architecture.md](./vue_architecture.md) 5절).

기능 간 계약은 **이름 있는 객체 하나**로 넘긴다. 위치 인자 나열은 순서가 바뀌면 조용히 깨진다 — 직전 프로젝트의 5개 위치 인자 emit이 그 사례였고, 현재는 `request-detail`이 `cityId` 하나만 넘긴다(`WeatherCard.vue:22`).

## 6. 도메인 데이터 구조

이 절의 모양이 그대로 Pinia state 모양이 된다.

### 핵심 결정

**① City와 Weather를 분리한다.** 예보(F-11)는 도시 1개에 관측 N개가 필요한데 합친 모델로는 표현이 부족하다. 화면 결합은 표시용 뷰모델로 해소한다.

**② status는 코드값(`statusCode`)과 표시 문구(`status`)를 함께 둔다.** `[현재]` — `weatherRules.js:classifyStatusCode`가 OpenWeatherMap의 수치 조건코드를 정규화한다. 문자열 정확 일치로 판정이 조용히 거짓이 되는 문제는 해소됐다(4.3절).

**③ DogProfile은 견종명을 저장하되, 판정은 DogTraits만 본다.** 견종명을 저장하는 이유는 화면 표시와 재편집 때문이고, 판정이 견종명을 보지 않는 이유는 4.4절 조합 폭발 때문이다. **저장 모델과 판정 입력 모델을 일부러 다르게 둔다.**

**④ 저장 단위를 고정한다.** 온도는 항상 섭씨, 표시 직전에만 변환. 체중은 kg. 풍속은 m/s — `[현재]` 실데이터(OpenWeatherMap `units=metric`)로 전환되며 목업 값(10~60, km/h 감각)이 만들던 단위 착시는 해소됐다. 강풍 임계값(`DANGER_WIND_SPEED`)을 50→14로 재보정해 반영했다(4.3절).

### 모델 정의

| 모델 | 핵심 필드 | 상태 |
| --- | --- | --- |
| `City` | `id`, `name`, `apiQuery`, `lat/lon` | `[현재]` — `api/cityMaster.js`(id/name/apiQuery), lat/lon은 OpenWeatherMap 응답의 `coord`에서 채운다 |

### 프로필을 비로그인 저장 허용으로 결정한 근거

직전 문서는 즐겨찾기(F-14)의 로컬 저장을 **거부**했다. 사유는 "병합 규칙(중복·우선순위)이 추가로 필요해지고, 이 프로젝트는 이미 같은 데이터를 여러 벌 두는 문제를 반복하고 있다"였다.

프로필(F-27)에는 같은 결론을 적용하지 **않는다.** 세 가지가 다르다:

1. **없으면 서비스가 동작하지 않는다.** 즐겨찾기는 없어도 날씨를 볼 수 있지만, 프로필이 없으면 판정 자체가 불가능하다(4.6). 로그인 벽을 세우면 첫 방문자는 아무것도 못 본다.
2. **컨셉과 정면 충돌한다.** 산출물이 "지금 나가도 되는가"인데, 판단하려는 사용자가 계정을 만드는 동안 판단을 미루게 된다 — 직전 문서가 날씨 조회를 비로그인으로 연 것과 같은 논리다.
3. **병합 규칙이 단순하다.** 즐겨찾기는 두 집합의 합집합 규칙이 필요했지만, 프로필은 **서버 우선**(로그인 시 서버 데이터로 대체, 로컬은 백업 유지) 한 줄로 끝난다.

규칙: 산책 판정 계열은 어떤 경우에도 로그인을 요구하지 않는다 / 로그인 요구는 여러 기기 동기화를 원할 때만 발생한다 / 한 흐름에서 로그인 요구는 한 번만.

## 8. 오류와 예외 정책

> 사용자의 입력이 정상 처리됐으나 대상이 없는 것은 오류가 아니다.

| 구분 | 정의 | 다음 행동 |
| --- | --- | --- |
| 빈 상태 | 요청 성공 + 결과 0건 | 입력을 바꾼다 |
| **초기 상태** | 아직 입력하지 않음(프로필 없음) | 입력을 시작한다 |
| 오류 상태 | 요청 실패 또는 대상 무효 | 다시 시도하거나 다른 화면으로 |

**초기 상태를 별도로 두는 이유**: 프로필 없음은 실패도, 결과 0건도 아니다. 셋을 같은 화면으로 처리하면 첫 방문자가 자기 잘못이라고 느낀다. 직전 프로젝트에서 통신 실패를 "검색 결과 없음"으로 표시했던 실패의 변형이다.

| 유형 | 구분 | 표시 | 재시도 |
| --- | --- | --- | --- |
| 프로필 없음 | 초기 | 온보딩 안내 + 등록 버튼 | — |
| 미등록 견종 | 빈 상태 | 기본 특성 적용 안내 + 직접 선택 유도 | — |
| 검색 결과 0건 | 빈 상태 | 일치 지역 없음 + 초기화 (`WeatherList.vue:19`) | — |
| 존재하지 않는 도시 | 오류 | 지역을 찾지 못함 + 목록 이동 | 불가 |
| API 실패/네트워크 단절 | 오류 | 불러오지 못함 + 재시도 (`ErrorState.vue`) | 가능 |
| **예보 조회 실패** | 오류 | **현재 판정은 유지하고 타임라인만 접는다** | 가능 |
| 잘못된 URL | 오류 | 주소 없음 + 홈 이동 | 불가 |

예보 실패를 부분 실패로 처리하는 이유: 지금 판정(F-23)은 현재 관측만으로 성립한다. 타임라인이 실패했다고 판정 전체를 오류로 만들면, 사용자는 볼 수 있었던 답을 잃는다.

**오류 메시지 원칙**: 한 문장에 (무엇이 일어났는가 + 무엇을 할 수 있는가) / 기술 용어 노출 금지 / 서로 다른 원인을 "또는"으로 묶지 않는다 / 서버 메시지를 그대로 출력하지 않는다.

| 시간별 예보(F-11, F-26 원천) | OpenWeatherMap `/data/2.5/forecast` | 동일 | **P0** | `api/weatherApi.js:fetchForecast` |
| 대기질(F-12) | OpenWeatherMap `/data/2.5/air_pollution` | 동일 | P1 | `api/weatherApi.js:fetchAirQuality` |
| 노면온도 실측(F-25 보조 원천) | 기상청_도로기상관측자료(data.go.kr 15159045, apihub.kma.go.kr) | `authKey`(`VITE_KMA_AUTH_KEY`) | **P0** | `api/roadWeatherApi.js:fetchAllRoadStations` |

이 넷은 모두 커스텀 백엔드 엔드포인트가 아니라 **외부 서비스를 axios로 직접 호출**한다(`vue_architecture.md` 9절 "Store는 axios를 직접 호출하지 않고 반드시 api/ 모듈을 거친다"는 원칙은 유지 — api/ 계층이 그 외부 호출을 감싼다).

**응답 공통 규격은 적용되지 않는다.** 위 봉투 구조(`{ok, data, meta}` / `{ok:false, error}`)는 자체 백엔드를 전제로 한 설계였는데, 실제로는 그런 백엔드가 없다. 각 외부 API는 자기 고유의 성공/실패 형식을 쓰고, `api/` 계층의 어댑터가 그 차이를 흡수해 8절의 오류 유형(`API_ERROR`/`FORECAST_ERROR` 등)으로 정규화한다.

### 9.2 기상청_도로기상관측자료 실측 스펙 `[현재]`

문서 조사만 하던 이전 상태에서 진전됐다 — 실제 호출·응답을 확인했다.

| 항목 | 실측 내용 |
| --- | --- |
| 응답 형식 | **JSON이 아니라 EUC-KR 텍스트 표.** `Content-Type: text/plain;charset=EUC-KR` |
| 구분자 | mode(조회 방식)에 따라 다르다 — mode=3(전체 관측점, 특정 시각)은 콤마+공백 구분, mode=1(단일 관측점, 시간 범위)은 콤마 없는 고정폭 공백 구분 |
| 필드 순서 | TM,STN_ID,STN_KO,ROAD_NM,STN_SP,LAT,LON,HT,SFS,**TR1(노면온도)**,VS,HM(습도),RN_DAY,SD,TA(기온),WD1,WS1,WD_INS,WS_INS,PS,CH1,CH2,CH3,CA (24개) |
| 결측값 | `-999` / `-999.0` |
| **CORS** | **지원하지 않는다** — `Access-Control-Allow-Origin` 헤더가 없다(curl로 실측 확인). 브라우저 직접 호출은 차단된다 |
| 관측점 좌표 | mode=3 스냅샷 응답 자체에 각 관측점의 `LAT`/`LON`이 포함돼 있어, 별도 관측점 마스터 데이터 없이도 최근접 탐색이 가능하다 — 이전 개정이 우려했던 "관측점 좌표 데이터 부재" 문제는 해소됐다 |

**CORS 미지원의 실질적 결과**: 이 프로젝트는 백엔드가 없다는 전제(9절 서두)와 정면으로 부딪힌다. 개발 서버는 `vite.config.js`의 프록시(`/kma-api`)로 우회하지만, **정적 빌드 배포(`dist/`)에는 이 프록시가 없다.** 운영 환경에서 이 API를 실제로 쓰려면 별도 서버리스 프록시(예: Cloudflare Worker, Vercel Function)가 필요하다 — `[결정 필요]`로 남는다. 이 한계 때문에 배포된 서비스는 사실상 항상 지면온도 추정 경로를 탄다(관측점 반경 밖인 경우와 같은 폴백이지만, 원인이 커버리지가 아니라 배포 환경이라는 점이 다르다).

### 9.3 여전히 자체 엔드포인트가 필요한 것 `[예정]`

| 메서드 | 경로 | 용도 | 우선순위 |
| --- | --- | --- | --- |
| GET | `/breeds` | 견종 마스터 + 특성 4축 | P0 |
| GET/PUT | `/profiles` | 프로필 서버 동기화 | P2 |
| POST | `/auth/*` | 인증 | P2 |

`/breeds`가 P0인 이유는 그대로다 — 견종 변환표는 데이터 양이 크고 갱신이 필요해 상수로 두기 어렵다. 다만 **최소 집합은 상수로 번들에 포함**해 네트워크 실패 시에도 판정이 동작하게 한다. `/cities`는 폐기한다 — 도시 목록은 `api/cityMaster.js`에 상수로 고정돼 있고(8개), 이 규모에서는 API로 받을 이유가 없다.

### Mock → API 교체 원칙

> 목업과 API 응답은 같은 도메인 모델로 화면에 도착해야 한다. 변환은 경계에서 한 번만 한다.

바뀌지 않아야 하는 것: 도메인 모델 필드명·타입, 도시 식별자 체계(`city_01`), 단위 규약, 판정 임계값. 바뀌는 것: 데이터 획득 경로, 동기→비동기, 실패 가능성. `[현재]` 이 원칙대로 `weatherStore.loadCityWeather()`의 이름·시그니처는 목업 시절과 동일하게 유지된 채 내부만 실제 axios 호출로 바뀌었다.

**비밀값**: API 키를 소스에 커밋하지 않는다. 직전 상태에서 동일 키가 3개 파일에 하드코딩된 채 git 추적 중이었다 — `.env`로 옮기는 것만으로는 안전해지지 않으며(이력에 남음), **재발급이 필요하다.** `[현재]` OpenWeatherMap·기상청 키는 `.env.local`(gitignore 대상)에만 있고, 커밋되는 것은 값이 비어있는 `.env.example`뿐이다.

## 10. 광고 정책

> 광고 영역을 둔다. P2다.

| 화면 | 허용 | 개수 |
| --- | --- | --- |
| 지역 목록 / 지역 상세 / 서비스 안내 | 허용 | 화면당 최대 1 |
| **산책 판정 화면** | **금지** | 0 |
| **시간대 타임라인** | **금지** | 0 |
| 프로필 등록·편집 / 404 / 오류·빈 상태 블록 내부 | 금지 | 0 |

**산책 판정·타임라인 금지 이유**: 이 두 화면은 "지금 우리 개를 데리고 나가도 되는지" 판단하려는 사용자만 온다. 광고는 정의상 주의를 다른 곳으로 돌리기 위해 존재하므로, 판단을 돕는 화면에 판단을 흩트리는 요소를 놓는 것은 컨셉과 정면 충돌한다. 직전 문서가 위험 경보 화면을 금지한 것과 같은 논리이며, 새 컨셉에서는 그 화면이 서비스의 중심이라 금지 범위가 넓어진다.

원칙: 화면당 최대 1개 / 스크롤 없이 보이는 첫 영역 금지 / 핵심 정보 블록 사이에 끼지 않는다 / 조작을 가로채지 않는다 / 광고임을 명시한다 / 로딩 실패는 조용히 슬롯을 접는다. **어떤 기능도 광고 시청으로 잠그지 않는다** — 이전 초기 기획서 단계에 있던 "10초 시청 후 콘텐츠 unlock" 게이트 방식은 이 원칙과 충돌해 채택하지 않았다(경로 추천 기능 자체도 F-ID가 없어 채택되지 않았다).

### `[현재]` 실제 연동 — Google Ad Placement(adBreak), 테스트 모드

`components/common/AdBreakSlot.vue`가 지역 날씨 화면(`/weather`)에만 배치돼 있다. **순수 보상형(선택)**으로만 쓴다 — 사용자가 "광고 보기"를 누르지 않아도 화면의 어떤 기능도 막히지 않는다(위 원칙과 동일선상). `index.html`에 `data-adbreak-test="on"`으로 테스트 모드 스크립트를 심어뒀다.

**`[결정 필요]`로 남는 것**: Google Ad Placement API는 정책상 **게임 콘텐츠 전용**이다(developers.google.com/ad-placement/docs/test). 왈씨는 게임이 아니므로, 테스트 모드를 벗어나 실제 광고를 서빙하려면 표준 AdSense 디스플레이 광고 단위(`<ins class="adsbygoogle">`)로 교체하는 것이 정책에 맞다 — 지금은 연동 경로를 시연하는 테스트 모드로만 유지한다. `VITE_ADSENSE_CLIENT_ID`도 아직 Google 공식 예시 placeholder(`ca-pub-123456789`)다.

시각 규격은 [design_architecture.md](./design_architecture.md), 컴포넌트 구조는 [vue_architecture.md](./vue_architecture.md) 소관.

## 11. 책임 경계

> 이 절은 새 컨셉에서 신설됐다. 판정 대상이 사람에서 동물로 바뀌면서 생긴 고유 리스크를 다룬다.

직전 컨셉에서 판정이 틀리면 사용자가 비를 맞았다. 새 컨셉에서 판정이 틀리면 **동물이 다칠 수 있다.** 직전 문서는 "업무상 법적 책임이 필요한 종사자"를 대상에서 배제했는데, 반려동물 건강 판정은 그 경계에 가깝다.

| 항목 | 규칙 |
| --- | --- |
| 판정 문구 | **단정하지 않는다.** "괜찮습니다"(X) / "15분 이내, 그늘 위주로"(O) |
| 추정값 표기 | 실측 관측점 밖 지역은 지면온도에 "추정"을 병기(4.2) |
| 근거 공개 | 어떤 값이 판정을 만들었는지 사용자가 확인할 수 있어야 한다(F-30) |
| 의료 판단 | **하지 않는다.** 질병·증상·투약 관련 기능은 채택하지 않는다(1.3) |
| 면책 표시 | 판정 화면에 상시 노출. P4 크기이되 숨기지 않는다 |
| 안전 쪽 기본값 | 정보가 부족하면 보수적으로 판정한다(미등록 견종, 다견 최취약 기준) |

> 정보가 부족할 때 낙관적으로 판정하지 않는다. 판정을 못 하는 것보다 잘못 안심시키는 것이 나쁘다.

면책 문구는 법적 방어 장치가 아니라 **서비스 성격의 정직한 표시**로 다룬다 — 이 서비스는 참고 정보를 제공하며 수의학적 진단을 대체하지 않는다.
